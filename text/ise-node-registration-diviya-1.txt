Pre-Registration Checks
Perform these checks before starting registration; they prevent avoidable failures.
IDENTITY & SOFTWARE
• Joining node should be in Standalone state.
• Use the correct node FQDN/hostname.
• Verify same ISE version and patch level before joining.
• Confirm the required GUI/admin credentials are available
INFRASTRUCTURE
• Forward and reverse DNS must resolve correctly.
• NTP/time must be synchronized across nodes.
• Validate Admin-certificate trust and complete certificate 
chains.
• Confirm routing, firewall rules, and required inter-node 
ports.
• Check latency/connectivity between PAN and the joining 
node.

Registering Nodes: Full Sync
• Export the configuration DB up to current 
system change number
• Upload the the database export (.dmp file) 
to registering node
• A checksum is sent to detect file corruption
• Receiving node stops app server (DB is up 
during import), uses the .dmp file to import 
data
• After app server is started secondary node 
updates primary that it completed sync 
successfully via JGroups
• If any step fails, the node is marked as 
‘Registration Failed’.

Node Replication (Uses JGroups)
• Replication is distinct from full sync
• Events on Primary PAN ‘replicated’ to all nodes as they happen
• PAN writes the events to its transaction table
• Separate threads picks the information and Publishes the changes
• Secondary nodes receive the changes and update its DB
• Secondary nodes can ask for missed messages
• Transaction table can store certain number of messages and secondary nodes 
can fetch and get in sync 
• PAN doesn’t wait for ACK from Secondary nodes
• Ordering is undertaken by JGroups

Node status in a Cisco ISE
• IN PROGRESS : No action is required if the status changes to ‘Connected’. If it changes to any 
other state, check respective message and action accordingly
• NOT_IN_SYNC (Critical limit is reached) : PAN stores up to 2M or 5 hours of unpublished 
messages. Once this limit is reached all nodes will be marked as Out-Of-Sync. A manual sync is 
required to recover
• REPLICATION_STOPPED : Secondary nodes are not reachable via JGroups. Once the nodes 
are reachable, the replication could recover automatically
• DISCONNECTED : Secondary nodes are not reachable via JGroups for 5 minutes or more. The 
node may come back up by itself when the underlying issue resolves. If not, log in to the Cisco 
ISE GUI and perform a manual synchronization from the Deployment window.
• REGISTRATION FAILED : If any step before successful sync from secondary node to PAN, we 
get this error

Registration / Sync Fails – Sanity Checks
• Verify DNS and NTP configuration (no alarms)
• Ensure Admin certificates are CA-signed with complete chains
• If Self-signed certificate, then ensure that the certificates are trusted between the nodes
• Validate open Ports: 443
• On PAN we need to ensure open Port : 12001 (JGroup)
• Test Telnet connectivity between PAN and registering node

The chart illustrates a 100% increase in database dump completion timeout limits starting from version 3.1 P8.
Key Insights
• Pre-3.1 P8 versions are restricted to a 2.5-hour completion 
window
• Version 3.1 P8 and above doubles the allowed timeout to 5 hours
• Extended limits accommodate larger data volumes and complex 
export processes
Conclusion
Upgrade to version 3.1 P8 or higher to leverage extended 5-hour 
timeout windows, ensuring successful completion of large-scale 
database dump operations without premature termination.

--- PAGE 21 ---
Scenario 1: Node Stuck at 0% Sync / Registration Fails
Root Cause: 
Network bandwidth or connectivity issue between PAN and remote PSN site (often MPLS 
WAN link)
Resolution: 
1. Run the bandwidth test (transfer a large backup file to both local and remote 
repositories) 
2. If remote is significantly slower, work with network team to ensure adequate 
bandwidth 
3. Consider scheduling registration during off-peak hours

--- PAGE 22 ---
Scenario 2: Replication Stopped
Symptoms: 
• Node status: "Replication Stopped" (connected on 443, not on 12001)
• Packet capture shows TCP retransmissions on port 12001

--- PAGE 23 ---
Scenario 2: Replication Stopped — Port 12001 Issues
Root Cause: 
Network device (firewall, IPS) blocking or rate-limiting TCP port12001
Resolution: 
1. Capture traffic on port 12001 between PAN and affected PSN 
2. Check for firewall ACLs, QoS policies, or IPS signatures blocking port 12001 
3. Verify iptables on both nodes allow port 12001 communication
4. Perform manual sync after network issue is resolved

Scenario 3: All Secondary nodes are going out of Sync simultaneously
Root Cause:
PAN unpublished rate crosses the threshold limit
Resolution: 
1. Reload PPAN to clear memory 
2. Perform manual sync on all nodes after PPAN comes back up
