CE1400V (1)
Security Best Practices for Virtualization in the DMZ
• Reduce Virtualization Risk
• Deploy one VM per host to eliminate lateral movement.
• Treat ESXi as a single-purpose appliance.
• Manage the host as a standalone system (no vCenter, no vMotion, no clustering).
• Enforce strict mapping: Physical NIC : vSwitch : Port Group : vNIC = 1 : 1 : 1 : 1
• Management Access Only From Inside
• ESXi management (HTTPS, SSH, APIs) allowed only from internal trusted management networks.
• Firewall rule: internal → ESXi mgmt, deny all other paths.
• ESXi patching and upgrades allowed only from internal networks.
• Use a Dedicated Management Interface (DMI) on Expressway for appliance administration.

CE1400V (2)
Security Best Practices for Virtualization in the DMZ

• Track state changes (services, network configuration, host operations).

Datacenter Failover
• In case one of the datacenter goes down, the other Expressway clusters act as backup
• Clients are spread across one or more backup Expressway clusters
• Load distribution in backup datacenters is statistical (based on DNS SRV Priority)
• Inter-cluster feature to be released for Jabber and Webex app
• Endpoints might require a reboot
• Rehoming to the original cluster once the datacenter is restored is not immediate. This happens when the clients 
perform a new service discovery

Digital Certificates and EKU
Whatisa DigitalCertificate?
A digital certificate is an electronic credential issued by a trusted Certificate 
Authority (CA) that:
• binds a public key to an identity and 
• enables authentication and integrity
• In protocols such as TLS, it allows peers to verify identities and 
securely establish encrypted sessions.
• Commonly used for TLS, code signing, and email security
A certificate contains:
• Subject information (the certificate holder)
• A public key
• Issuer information (the CA)
• A validity period
• Extensions such as Extended Key Usage (EKU)
WhatisEKU(ExtendedKeyUsage)?
EKUis an X.509certificateextensionthat specifiesintendedpurposesfor
the certificate.
• It restrictshow the certificate can be usedbeyondthe basickeyusage.
• Someexamplesof EKUvalues:
• ServerAuthentication(id-kp-serverAuth) → For HTTPSservers.
• ClientAuthentication(id-kp-clientAuth)→ FormutualT L Sclients.
• CodeSigning→ Forsigningsoftware.
• Email Protection→ Forsecuringemails.
HowEKUisUsed
Browsers,operatingsystems,and applicationscheckEKUbefore 
trustinga certificate for a specificfunction.
• If EKU does not match the required purpose, the certificate is rejected for that use.
• Example:
• A certificate with only clientAuth EKU cannot be used for a
web server.
• A certificate with serverAuth EKU is valid for HTTPS.

Chrome Root Policy
The Chrome Root Program Policy establishes the minimum requirements that a root Certification Authority (CA)
certificate must meet to be included and remain trusted by default in the Google Chrome web browser's Root Store. 
(Chrome Root Program Policy)
• Core Requirements for Trusted Root CAs
• CAs must comply with CA/Browser Forum Baseline Requirements and Chrome-specific checks.
• No more mixed-use roots; ServerAuth-only hierarchies required for public server TLS by June 15, 2026
• ClientAuthEKU Sunset: All new public TLS server certificates must omit clientAuthby June 15, 2026, enforced
gradually starting mid-2025
• Chrome Root Policy is followed by Chromium-based Browsers (Eg. Chrome, Edge, Opera, Brave, Samsung)

Response from Public CA providers
• Sept-Oct 2025
• Many public CAs began *not including clientAuth EKU by default* for newly issued public TLS certs.
• Examples: DigiCert, Sectigo, SSL.com, they shifted to serverAuth EKU only by default and require explicit request 
to include clientAuth during an interim period.
• Typical vendor notes: Oct 1, 2025 (DigiCert start default change); Sept/Oct 2025 timelines
• from others.
• May 1 – Jun 15, 2026
• Public CA vendors plan to remove the option to issue new public TLS certs with clientAuth EKU entirely
• Dates may vary: some vendors start by May 1 / May 15, others point to industry enforcement around Jun 15, 2026
• Certificates issued before these cutoff dates generally remain valid until they expire.
• After these dates, public CAs will no longer issue TLS certs usable for client authentication
• Organizations must migrate to private CAs or alternative authentication methods for mTLS/client-auth use cases.

Host-Based Intrusion Protection
• Expressway includes a host-based intrusion protection system (fail2ban)
• When enabled, Expressway scans logs for signatures, and establishes dynamic rules to block source ip 
addresses
• This protects against brute force attacks that originate from a single source ip address
• When a blocked IP tries to access the system, the request is dropped by the firewall and no response is 
sent back to the source

VDI Architectures

--- PAGE 66 ---
© 2026 Cisco and/or its affiliates. All rights reserved.
VDI Architectures
• The objective of VDI architectures is to enable the use of thin clients, with all application 
processing performed on Hosted Virtual Desktops (HVDs) deployed in the datacenter.
• While messaging functions operate well within the standard VDI architecture, media traffic (voice 
and video) can cause a "hairpin effect," where media streams loop through the datacenter, 
potentially saturating bandwidth.
• To mitigate this, Cisco has developed optimized VDI architectures for Jabber and Webex app that 
offload media processing to the local thin client, enabling direct media paths between endpoints 
and avoiding the hairpin effect. This approach preserves bandwidth and improves media quality.
BRKCOL-2125

--- PAGE 67 ---
© 2026 Cisco and/or its affiliates. All rights reserved.
VDI Environment Overview
• Connection broker - The resource and connection manager (Citrix, VMware) that connects the virtualization provider to 
the thin client. Manages user authentication and connection to virtual desktops 
• Hosted virtual desktop (HVD) - The Virtual Machine (VM) that runs the Webex App/Jabber remotely.
• Thin client - The endpoint (for example, low profile or repurposed desktop or laptop) that the user uses to sign in 
remotely to the virtual desktop. The Citrix Workspace App or VMware Horizon Client and the VDI plugin are installed on 
this device to access the HVD environment.
• VDI Plugin - Software that is installed on the thin client used to offload media processing to the user device instead of 
HVD resources (Citrix Workspace App and VMware Horizon Client)
• Access Gateways - If the thin client is off-premises, then Citrix/VMWare access gateways are required to connect to 
the HVD
